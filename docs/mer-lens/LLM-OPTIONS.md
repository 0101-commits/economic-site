# 메르 리스크 렌즈 — LLM 제공자 선택 메모

## 결론

**바꿀 것 없다.** 오늘 겪은 "Gemini 가 잘 안 된다"는 죽은 키(401)와 퇴역 모델(404) 두 가지가
원인이었고 둘 다 오늘 고쳤다. 새 키 + `gemini-3.1-flash-lite` 조합으로 349편 중 348편이
성공했다(실측, 2026-09-15). 제공자를 바꿀 이유가 아니라 **조용히 죽는 것을 드러내는 장치가
없다는 것**이 더 큰 문제다 — 이 부분은 아래 5번에 따로 적었다. Cloudflare Workers AI 는
매력적으로 보이지만 이 작업(2,800자 한국어 원문에서 스키마 20여 필드를 인용과 함께 뽑는 구조화
추출)에는 검증 없이 갈아탈 근거가 없다. Anthropic 은 사용자가 배제했으므로 후보에서 뺐다.

## 각 선택지

**Gemini(현 상태 유지)** — 오늘 실측(349편 중 348편 성공, 96자짜리 원문 1편만 실패)은 이 조합이
이미 이 작업에 맞는다는 근거다. `gemini-flash-latest` 별칭은 살아있지만 과부하 503 이 잦아
(3/3 실패 실측) 1순위에 두지 않는 현재 코드 판단은 유지할 만하다. 429 는 20초 재시도, 404(모델
퇴역)는 별칭 폴백으로 이미 방어돼 있다.

**Cloudflare Workers AI** — 무료라는 매력은 있지만, `/ai` 핸들러는 애초에 "단발 질의응답·브리핑"
용으로 설계됐다(서버 고정 프롬프트 3종: 브리핑/QA/스터디, `ALERTS_SYNC_KEY` keyHash 로 프론트
호출만 인증). 813편을 순회하며 구조화 JSON을 뽑는 배치 작업에 재사용하려면 ① 새 서버 고정
프롬프트 모드 추가 ② 배치 스크립트가 매 편마다 이 Worker를 호출하도록 인증·요청 경로를 새로
설계 ③ Workers AI 무료 한도(일 10,000 Neurons)가 813편 백필 + 월 65편 증분을 감당하는지 확인,
이 세 가지가 필요하다. 무엇보다 **품질을 실측하지 않았다** — `env.AI` 바인딩이 실제로 켜져
있는지조차 시크릿 없이는 확인 불가(wrangler.jsonc 에 `"ai": {"binding": "AI"}` 설정은 있지만,
이건 API 키 시크릿과 달리 배포 시 자동 적용되는 리소스 바인딩이라 별도 시크릿 등록 없이도 이미
켜져 있을 가능성이 높다 — 다만 실제 호출 성공 여부는 배포된 Worker에 직접 요청을 넣어봐야
확인된다). 소형 오픈모델(llama-3.1-8b 급)로 "인용을 원문에서 그대로 떠오기"라는, 지어내면
안 되는 작업을 시키는 건 Gemini flash-lite보다 실패율이 높을 것으로 보이나 이는 추정이다.

**Anthropic** — 기획안 §5.3 은 Opus 5 를 품질 기준 권고안으로 명시했고(백필 ≈$31, Batch ≈$16,
증분 ≈$2.5/월), 코드에도 이미 배선돼 있다(GHA 시크릿 슬롯, `mer_extract.py` 의
`provider()` 가 `ANTHROPIC_API_KEY` 를 최우선으로 본다). 그러나 사용자의 자격증명 메모에
"claude api는 제외"라고 명시돼 있으므로, 코드가 지원한다는 사실과 별개로 채택하지 않는다.

**OpenAI / Vertex AI / 로컬 모델** — 셋 다 지금 키가 없거나(OpenAI), 인증 방식이 API 키보다
무거워지거나(Vertex), GHA 클라우드 러너에서 애초에 실행할 수 없다(로컬 모델은 이미 기획된
"PC에서 1회 백필"과는 별개로, 그 백필 자체를 로컬 LLM으로 돌리자는 제안이 될 텐데 검증 비용만
크고 이득이 안 보인다). 셋 다 지금 갈아탈 근거가 없다.

**규칙만(LLM 제거)** — 정규식 스캔은 이미 있고 813편 전수를 돈다. 실측 비교: 임계선(트리거
조건문) 201건 대 LLM 358건, 즉 LLM 이 1.8배 더 찾는다. 더 결정적인 건, 영향 엣지 810개·인과
사슬 326개·자산별 스탠스 341건은 "지표A가 오르면 자산B가 내린다" 같은 **자유 서술** 관계라
정규식으로는 애초에 만들 수 없다(기획안 §3.7 "외국인 수급 14편"은 정규식 한계의 실증 사례로
이미 기록돼 있다). 이 축소안을 택하면 전이 경로 맵(기획 §6 핵심 화면 후보 1순위) 이 통째로
빠진다 — LLM 없이 가는 안은 "덜 좋은 렌즈"가 아니라 "다른 제품"이 된다.

## 진짜 위험 — 제공자보다 "조용한 정지"

오늘의 실패 패턴을 일반화하면: 제공자가 모델을 예고 없이 퇴역시키고(Gemini 2.0/2.5-flash 가
2026-09-15 기준 404), 키가 조용히 죽고(GHA `GEMINI_API_KEY` 가 401), 이 실패가
`continue-on-error: true` 뒤에 묻힌다(실측 — `fetch-data.yml` 의 `Extract 메르 글 구조화` 스텝은
`continue-on-error: true` 이고, 이 워크플로 전체에 `DISCORD`/`failure()`/`always()` 조건의
실패 알림 스텝이 **하나도 없다**, grep 확인). 코드에 있는 방어는 404 폴백(별칭 모델로 전환),
401/403 조기 중단(남은 편을 헛되이 재시도하지 않고 로그에 원인을 남김), 429/503 1회 재시도
세 가지뿐이다. **없는 것**: 이 실패가 사람에게 전달되는 경로. GHA 로그는 아무도 상시 보지
않고, `continue-on-error` 는 Actions UI 를 초록으로 유지해 실패를 숨긴다. 오늘도 "며칠간 조용히
0건씩 실패"를 사람이 직접 물어봐서 발견했지, 시스템이 알려주지 않았다. 제공자를 몇 개 더
배선해봐야 이 구조적 공백은 그대로 남는다 — **다음에 우선할 일은 대안 제공자 추가가 아니라
실패 가시화**라는 게 이 조사의 결론이다.

## 나중에 할 일(우선순위 순, 제공자 교체 아님)

1. **실패 가시화** — `mer_extract.py` 가 401/403 조기 중단할 때, 혹은 GHA 스텝이 실패할 때
   디스코드(이미 이 계정에 알림 인프라가 있다 — `project_cli_notify_plan` 메모리 참고)나 최소
   워크플로 Job Summary 에 남기는 스텝 추가. `continue-on-error` 를 없애자는 게 아니라
   (다른 스텝을 막으면 안 되므로), 실패를 "숨기지 않고 알리는" 스텝을 별도로 붙이는 것.
2. **Cloudflare Workers AI 실측** — 배포된 Worker 에 `GET /ai?test=1` 류의 진단 호출을 추가하거나
   `DEBUG_MODE=1` 로 한 번 켜서 `env.AI` 바인딩이 실제로 응답하는지, 그 응답 품질이 mer 추출
   스키마를 감당하는지 소표본으로 확인. 무료라는 장점이 크므로 검증은 해볼 가치가 있으나,
   지금 급한 일은 아니다.
3. Anthropic/OpenAI/Vertex 는 사용자 결정(자격증명 제외, 미보유, 이득 없음)이 바뀌지 않는 한
   재검토 불필요.
